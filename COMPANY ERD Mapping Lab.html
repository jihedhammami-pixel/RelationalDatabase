Take inventory of the diagram

Before applying any rule, classify every construct. The algorithm handles entities first, so that every primary key exists before a foreign key needs it.

  • Strong entity types: EMPLOYEE, DEPARTMENT, PROJECT.
  • Weak entity type: DEPENDENT (double rectangle), identified through DEPENDENTS_OF (double diamond).
  • Binary relationships: MANAGES 1:1 · WORKS_FOR 1:N · CONTROLS 1:N · SUPERVISION 1:N recursive · WORKS_ON M:N.
  • Special attributes: Name is composite, Locations is multivalued, Number_of_employees is derived.
DEPARTMENT and PROJECT each have two underlined attributes (Name and Number): both are keys. We will pick one as primary key and keep the other UNIQUE.
1

Map the strong entity types

Rule · Step 1For each strong entity type E, create a relation R with all the simple attributes of E. For a composite attribute, keep only its simple components. Choose one key of E as the primary key of R.
  • EMPLOYEE: the composite Name is flattened into Fname, Minit, Lname; Ssn is the key, so it becomes the PK.
  • DEPARTMENT: Name and Number are both keys. We choose Number as PK (short, stable) and declare Name UNIQUE. Attributes are renamed Dname, Dnumber so they stay clear once relations are joined.
  • PROJECT: same reasoning: Pnumber is the PK, Pname is UNIQUE, Location becomes Plocation.
  • Postponed: the multivalued Locations waits for step 6; the derived Number_of_employees is not stored (see the end of the walkthrough).
EMPLOYEE(Fname, Minit, Lname, Ssn, Bdate, Address, Gender, Salary) DEPARTMENT(Dname, Dnumber) Dname UNIQUE PROJECT(Pname, Pnumber, Plocation) Pname UNIQUE
entity → relationcomposite → componentskey → PKother key → UNIQUE
2

Map the weak entity type

Rule · Step 2For each weak entity type W with owner E, create a relation R with the simple attributes of W, plus the primary key of E as a foreign key. The primary key of R is the owner's key combined with the partial key of W.
  • The owner of DEPENDENT is EMPLOYEE (through the identifying relationship DEPENDENTS_OF), so DEPENDENT receives Essn → EMPLOYEE.Ssn.
  • The partial key Name (dashed underline) becomes Dependent_name.
  • PK = (Essn, Dependent_name): two employees may each have a dependent called Alice.
  • The identifying relationship DEPENDENTS_OF needs no relation of its own: the FK Essn already represents it.
DEPENDENT(Essn, Dependent_name, Gender, Birth_date, Relationship) FK Essn → EMPLOYEE(Ssn) ON DELETE CASCADE
Use ON DELETE CASCADE: a dependent cannot exist without its employee (existence dependency).
3

Map the binary 1:1 relationship

Rule · Step 3 (foreign-key approach)For a 1:1 relationship between S and T, put the primary key of T as a foreign key in S, choosing for S the entity with total participation. Attributes of the relationship move to S too.
  • MANAGES links EMPLOYEE (1) and DEPARTMENT (1). The double line is on the DEPARTMENT side: every department has a manager, but most employees manage nothing.
  • So DEPARTMENT is S: it receives Mgr_ssn → EMPLOYEE.Ssn, declared NOT NULL (total participation).
  • The relationship attribute Start_date becomes Mgr_start_date in DEPARTMENT.
  • Mgr_ssn is also declared UNIQUE, because one employee manages at most one department. Without UNIQUE the relationship silently becomes 1:N.
DEPARTMENT(Dname, Dnumber, Mgr_ssn, Mgr_start_date) FK Mgr_ssn → EMPLOYEE(Ssn) NOT NULL, UNIQUE
Why not put the FK in EMPLOYEE?

It would work, but most employees are not managers: the column would be NULL in almost every row. Choosing the side with total participation avoids those NULLs.

The two other options of step 3 are a merged relation (only when both sides are total) and a cross-reference relation; neither fits here.

4

Map the binary 1:N relationships

Rule · Step 4For a 1:N relationship, identify the relation S on the N side. Put the primary key of the 1-side relation T into S as a foreign key, together with any attributes of the relationship.
  • WORKS_FOR (DEPARTMENT 1 : N EMPLOYEE): EMPLOYEE gets Dno → DEPARTMENT.Dnumber. Total participation of EMPLOYEE makes it NOT NULL.
  • CONTROLS (DEPARTMENT 1 : N PROJECT): PROJECT gets Dnum → DEPARTMENT.Dnumber, NOT NULL (every project is controlled).
  • SUPERVISION is recursive: the supervisee (N) side is EMPLOYEE and the supervisor (1) side is EMPLOYEE too. EMPLOYEE gets Super_ssn → EMPLOYEE.Ssn, named after the role. It may be NULL: the top manager has no supervisor.
EMPLOYEE(Fname, Minit, Lname, Ssn, Bdate, Address, Gender, Salary, Super_ssn, Dno) PROJECT(Pname, Pnumber, Plocation, Dnum)
Never put the FK on the 1 side: DEPARTMENT would need a list of employee numbers, which is not an atomic value.
5

Map the binary M:N relationship

Rule · Step 5For an M:N relationship, create a new relation containing the primary keys of both participants as foreign keys. Their combination is the primary key. Attributes of the relationship are added to it.
  • WORKS_ON links EMPLOYEE (M) and PROJECT (N): an employee works on several projects and a project has several employees.
  • New relation WORKS_ON with Essn → EMPLOYEE.Ssn and Pno → PROJECT.Pnumber; PK = (Essn, Pno).
  • The relationship attribute Hours belongs to the pair (employee, project), so it goes in WORKS_ON.
WORKS_ON(Essn, Pno, Hours)
An M:N relationship is always a separate relation, even when it has no attributes.
6

Map the multivalued attribute

Rule · Step 6For each multivalued attribute A of entity E, create a new relation with A and the primary key of E as a foreign key. The primary key is the combination of both.
  • Locations (double oval) belongs to DEPARTMENT: one department can be in several cities.
  • New relation DEPT_LOCATIONS with Dnumber → DEPARTMENT.Dnumber and Dlocation; PK = (Dnumber, Dlocation).
DEPT_LOCATIONS(Dnumber, Dlocation) e.g. (5, Bellaire) (5, Sugarland) (5, Houston)
Keeping Locations inside DEPARTMENT ("Bellaire, Sugarland, Houston") would break atomicity (1NF).
7

Map n-ary relationships

Rule · Step 7For each relationship with more than two participants, create a new relation with the primary keys of all participants as foreign keys (plus the relationship's attributes). Its primary key is usually the combination of these FKs.
  • Every relationship in the COMPANY diagram is binary, so step 7 adds nothing here.
  • We still check it: skipping a step on purpose is part of applying the algorithm correctly.
— no new relation —
✓

Handle the derived attribute

Rule · Derived attributesA derived attribute is not stored: it is computed from other data when needed, typically with a query or a view.
  • Number_of_employees (dashed oval) can be computed by counting the EMPLOYEE tuples of each department, using the FK Dno.
  • Storing it would create a value that becomes wrong after every hire or departure unless it is kept up to date automatically.
CREATE VIEW DEPT_SIZE AS SELECT Dno AS Dnumber, COUNT(*) AS Number_of_employees FROM EMPLOYEE GROUP BY Dno;

What foreign keys cannot enforce

Some participation constraints of the ERD have no equivalent in the schema. They must be enforced by triggers, assertions or the application:

  • Every DEPARTMENT has at least one employee (total participation of DEPARTMENT in WORKS_FOR).
  • Every EMPLOYEE works on at least one project, and every PROJECT has at least one employee (total participation on both sides of WORKS_ON).

Total participation on the N side of a 1:N or 1:1 relationship is captured by NOT NULL (Dno, Dnum, Mgr_ssn); total participation on the 1 side or in an M:N relationship is not.

Implementation

The schema in SQL

EMPLOYEE references DEPARTMENT (Dno) and DEPARTMENT references EMPLOYEE (Mgr_ssn): a cycle. We create the tables first, then add those two foreign keys with ALTER TABLE.

CREATE TABLE EMPLOYEE (
  Fname      VARCHAR(15)  NOT NULL,
  Minit      CHAR(1),
  Lname      VARCHAR(15)  NOT NULL,
  Ssn        CHAR(9)      PRIMARY KEY,             -- step 1
  Bdate      DATE,
  Address    VARCHAR(50),
  Gender     CHAR(1),
  Salary     DECIMAL(10,2) CHECK (Salary >= 0),
  Super_ssn  CHAR(9),                            -- step 4, SUPERVISION (nullable)
  Dno        INT          NOT NULL,                -- step 4, WORKS_FOR (total)
  FOREIGN KEY (Super_ssn) REFERENCES EMPLOYEE(Ssn)
);

CREATE TABLE DEPARTMENT (
  Dname          VARCHAR(25) NOT NULL UNIQUE,       -- alternate key
  Dnumber        INT         PRIMARY KEY,
  Mgr_ssn        CHAR(9)     NOT NULL UNIQUE,       -- step 3, MANAGES (1:1, total)
  Mgr_start_date DATE,
  FOREIGN KEY (Mgr_ssn) REFERENCES EMPLOYEE(Ssn)
);

ALTER TABLE EMPLOYEE ADD FOREIGN KEY (Dno) REFERENCES DEPARTMENT(Dnumber);

CREATE TABLE DEPT_LOCATIONS (                      -- step 6
  Dnumber   INT,
  Dlocation VARCHAR(15),
  PRIMARY KEY (Dnumber, Dlocation),
  FOREIGN KEY (Dnumber) REFERENCES DEPARTMENT(Dnumber) ON DELETE CASCADE
);

CREATE TABLE PROJECT (
  Pname     VARCHAR(25) NOT NULL UNIQUE,
  Pnumber   INT         PRIMARY KEY,
  Plocation VARCHAR(15),
  Dnum      INT         NOT NULL,                -- step 4, CONTROLS (total)
  FOREIGN KEY (Dnum) REFERENCES DEPARTMENT(Dnumber)
);

CREATE TABLE WORKS_ON (                            -- step 5
  Essn  CHAR(9),
  Pno   INT,
  Hours DECIMAL(3,1),
  PRIMARY KEY (Essn, Pno),
  FOREIGN KEY (Essn) REFERENCES EMPLOYEE(Ssn),
  FOREIGN KEY (Pno)  REFERENCES PROJECT(Pnumber)
);

CREATE TABLE DEPENDENT (                           -- step 2
  Essn           CHAR(9),
  Dependent_name VARCHAR(15),
  Gender         CHAR(1),
  Birth_date     DATE,
  Relationship   VARCHAR(8),
  PRIMARY KEY (Essn, Dependent_name),
  FOREIGN KEY (Essn) REFERENCES EMPLOYEE(Ssn) ON DELETE CASCADE
);
